# Bitrix Randomizer --- контекст проекта для ChatGPT

Последнее обновление: 2026-11-23

## 1. Назначение документа

Этот файл --- единый контекст проекта **Bitrix Randomizer**. Использовать его в последующих диалогах ChatGPT, чтобы продолжать проектирование и разработку без повторного сбора уже принятых решений.

Важно:
- Не выдавать непроверенные технические возможности REST API за подтверждённые.
- Перед реализацией спорных функций сверяться с актуальной официальной документацией Битрикс24.
- Приоритетная среда --- облачный Битрикс24, стандартный тариф.
- Цель проекта --- коммерческое приложение для публикации в Битрикс24 Маркетплейс.

## 2. Краткое описание продукта

**Bitrix Randomizer** --- приложение для Битрикс24, позволяющее администраторам создавать и сохранять собственные генераторы случайных данных, а затем использовать их в CRM-автоматизации через собственного робота.

Первоначальная проблема, из которой возникла идея: пользователю потребовалось получать случайное число на стадии сделки и выполнять разные действия в зависимости от результата. Штатный инструмент генерации случайных данных в бизнес-конструкторе оказался недоступен на используемом стандартном тарифе.

Приложение должно дать возможность генерировать случайные значения без необходимости использовать расширенный бизнес-конструктор.

Основной пользовательский сценарий:
1. Администратор устанавливает Bitrix Randomizer из Маркетплейса.
2. Открывает отдельный интерфейс приложения.
3. Создаёт и сохраняет один или несколько генераторов.
4. В CRM-автоматизации добавляет робота Bitrix Randomizer.
5. В настройках робота выбирает ранее созданный генератор.
6. Настраивает, куда сохранить результат.
7. При запуске робот генерирует значение и записывает его в выбранное поле сделки и/или возвращает значение как выходной параметр, если это поддерживается и подтверждено тестированием.

## 3. Цели и бизнес-модель

### 3.1 Цели

-   Создать самостоятельный тиражируемый продукт для Битрикс24 Маркетплейс.
-   Решить конкретную задачу CRM-автоматизации, в том числе для пользователей стандартного тарифа.
-   В перспективе получать доход от распространения приложения.
-   Заложить архитектуру, позволяющую расширять поддержку CRM-сущностей без переписывания ядра.

### 3.2 Коммерческие требования

-   Приложение должно быть пригодно для установки на множество независимых порталов.
-   Данные, настройки, токены и лицензии каждого портала должны быть изолированы.
-   Предусмотреть тарифы/лимиты приложения, если это допускает согласованная с Битрикс24 модель монетизации.
-   До разработки биллинга проверить правила Маркетплейса и определить допустимую модель: вознаграждение через Маркетплейс, самостоятельная оплата дополнительных возможностей или иная разрешённая модель.
-   Не считать, что любая SaaS-подписка автоматически допускается правилами Маркетплейса. Классификацию приложения и модель оплаты необходимо предварительно согласовать с Битрикс24.

## 5. Функциональные требования

### 5.1 Интерфейс приложения

Предусмотреть отдельную страницу Bitrix Randomizer внутри Битрикс24.

Основные разделы:
1. **Мои генераторы** --- список созданных генераторов.
2. **Создать генератор** --- форма создания и редактирования.
3. **История генераций** --- потенциальная функция последующих версий. Для MVP не используется.
4. **Настройки/тариф** --- потенциальная функция коммерческой версии. Для MVP не используется.

Для каждого генератора предусмотреть:
- название;
- уникальный внутренний идентификатор;
- тип генерации;
- параметры генерации;
- дату создания и изменения;
- принадлежность конкретному порталу;
- возможность редактирования, копирования и удаления.

Генераторы должны быть доступны для повторного использования в разных роботах и в разных воронках одного портала.

### 5.2 Типы генераторов первой версии (MVP)

**A. Числовые данные**
- случайное целое число в диапазоне от минимального до максимального значения (в том числе отрицательные).

**B. Текстовые данные**
- случайный текст заданной пользователем длины;
- предусмотреть возможность выбора алфавита: только русский, только английский, только цифры - и их любые комбинации;
- предусмотреть возможность выбора только заглавных, только прописных, оба варианта.

Для генераторов необходимо определить и валидировать граничные случаи: минимальное значение больше максимального, пустое значение, неверный тип данных.

### 5.3 CRM-робот

Приложение должно зарегистрировать собственного робота в CRM-автоматизации.
Предварительно рассматривается REST-метод `bizproc.robot.add`; точные параметры, обязательные права и ограничения нужно подтвердить по актуальной документации.

Предполагаемое поведение:
1. Администратор добавляет робота на стадию сделки.
2. В настройках выбирает сохранённый генератор.
3. Выбирает место назначения результата.
4. При выполнении робот определяет текущий портал и сделку.
5. Получает настройки выбранного генератора.
6. Генерирует значение.
7. Записывает значение в выбранное поле сделки и/или передаёт результат через выходные параметры, если поддерживается.
8. Корректно сообщает об ошибках.

### 5.4 Настройки робота

Минимальные настройки:
- выбор сохранённого генератора;
- выбор поля сделки для записи результата;
- проверка совместимости типа генератора с типом поля;
- понятное сообщение, если генератор удалён или недоступен;
- обработка отсутствующего/недоступного поля.

Интерфейс настроек должен загружать доступные генераторы и поля с учётом текущего портала и контекста робота.

### 5.5 Запись результата

**Основной подтверждаемый сценарий, который требуется реализовать и проверить первым:** запись сгенерированного значения в пользовательское поле текущей сделки через CRM REST API.

Необходимо учитывать:
- числовые значения записывать в числовые поля или текстовые поля;
- текстовые значения --- в совместимые строковые поля;
- не допускать некорректного преобразования типов;
- использовать идентификатор сделки из контекста выполнения робота;
- не позволять приложению записывать результат в сущность или портал, не относящиеся к текущему вызову.

### 5.6 Переменные CRM и выходные значения робота

Пожелание: результат генерации должен быть применим не только для записи в поле сделки, но и для использования в переменных CRM.

Рассмотреть два механизма:
1. **Выходные параметры собственного робота.** В документации роботов рассматривается `RETURN_PROPERTIES` и передача результата через `bizproc.event.send`. Нужно проверить фактический формат регистрации и возврата значений, а также их доступность в последующих роботах.
2. **Штатный робот «Изменение переменной».** Проверить, можно ли использовать выходное значение Bitrix Randomizer как источник для присвоения переменной CRM.

Важно: не считать наличие универсального REST-метода прямой записи CRM-переменной подтверждённым. Не проектировать прямую запись в переменные как готовую функцию, пока не проведён тест. Если прямой механизм недоступен, предпочтительный вариант --- вернуть выходное значение собственного робота и использовать штатный механизм Битрикс24, если совместимость подтвердится.

Для MVP обязательна проверка технической реализуемости. Если поддержка переменных не укладывается в первую версию, задокументировать ограничение и выпустить сначала запись в поле сделки.

## 6. Архитектурные требования

### 6.1 Общая архитектура

Предварительная схема:
- Frontend: интерфейс приложения, встроенный в Битрикс24.
- Backend/API: серверная логика приложения.
- Generator Core: независимый модуль генерации значений.
- Bitrix24 Integration: OAuth, REST API, регистрация робота, обработчики событий.
- CRM adapters: отдельный слой для работы с CRM-сущностями.
- Database: хранение порталов, генераторов, настроек, лицензий и истории.

Генератор не должен зависеть от конкретной CRM-сущности. Он принимает конфигурацию и возвращает значение. CRM-адаптер отвечает за чтение контекста и запись результата.

### 6.2 Расширяемость CRM-сущностей

В первой версии активен только адаптер сделок.

Архитектура должна позволять в будущем добавить:
- лиды;
- контакты;
- компании;
- смарт-процессы.

Не реализовывать эти адаптеры в MVP без отдельного решения. Не привязывать ядро генерации к полям сделки или `DEAL_ID`.

### 6.3 Многопользовательская модель

Приложение обслуживает множество независимых порталов.

Для каждого портала должны быть отдельные:
- идентификатор портала;
- OAuth-токены;
- настройки приложения;
- генераторы;
- история запусков;
- лицензия/тариф и лимиты.

Все запросы к данным должны быть ограничены идентификатором портала. Нельзя полагаться только на переданный клиентом `portal_id`: принадлежность портала необходимо подтверждать серверной сессией/контекстом OAuth и проверять на каждом запросе.

### 6.4 OAuth и безопасность

Для тиражного приложения использовать предусмотренный Битрикс24 OAuth-механизм, а не один общий входящий вебхук.

Требования:
- безопасное хранение access/refresh tokens;
- обновление токенов;
- минимально необходимые scopes;
- проверка входящих событий/контекста;
- защита от повторной обработки событий там, где это необходимо;
- секреты и ключи не хранить в исходном коде;
- логировать ошибки без утечки токенов и персональных данных;
- предусмотреть обработку отзыва доступа и удаления приложения.

### 6.5 Предварительный технологический стек

-   Backend: Python + FastAPI.
-   Database: PostgreSQL.
-   Frontend MVP: HTML, CSS, JavaScript.
-   Интеграция: REST API Битрикс24, OAuth 2.0.
-   Hosting: VPS или облачная инфраструктура.
-   React можно подключить позднее, если сложность интерфейса этого потребует.

Стек предварительный и может быть пересмотрен в проыессе разработки.

## 7. Предварительная структура данных

`portals` --- подключённые порталы Битрикс24.
`generators` --- основные записи генераторов.
`generator_configs` --- параметры и конфигурации генераторов.
`robot_executions` --- история выполнения роботов.
`licenses` --- тарифы, статус подписки и лимиты.
`crm_entities` --- справочник поддерживаемых типов CRM-сущностей.

Все пользовательские данные должны быть связаны с порталом. Окончательную нормализацию схемы выполнить при проектировании базы данных.

## 8. Нефункциональные требования

-   Изоляция данных разных порталов.
-   Устойчивость к повторным и параллельным вызовам робота.
-   Корректная обработка ошибок REST API и временной недоступности портала.
-   Понятные сообщения об ошибках в интерфейсе и логах.
-   Контроль типов значений и валидация конфигураций.
-   Возможность обновлять приложение без потери данных генераторов.
-   Удаление/деактивация данных в соответствии с правилами Битрикс24 и применимыми требованиями приватности.
-   Минимизация запрашиваемых прав доступа.
-   Возможность масштабировать серверную часть при росте количества порталов.

## 9. Критерии готовности MVP

MVP считается технически готовым, если:
1. Приложение устанавливается на тестовый портал.
2. OAuth работает корректно.
3. Администратор создаёт и сохраняет генератор.
4. Робот Bitrix Randomizer отображается в автоматизации сделок.
5. В настройках робота можно выбрать сохранённый генератор.
6. Робот запускается на нужной сделке.
7. Генерируется корректное значение.
8. Значение записывается в выбранное поле сделки.
9. Выходное значение передаётся последующим шагам, если этот механизм подтверждён и включён в MVP.
10. Данные разных порталов изолированы.
11. Повторная установка и обновление приложения не приводят к потере пользовательских настроек.
12. Приложение проходит тесты на целевом тарифе.

## 10. Технические вопросы, которые пока НЕ считаются решёнными

Следующие пункты требуют проверки по актуальной документации и экспериментом:

1.  Доступность `bizproc.robot.add` и выполнение зарегистрированного робота на тарифе "Стандартный".
2.  Точные обязательные scopes и права для регистрации/выполнения робота и изменения сделки.
3.  Точный формат регистрации обработчика робота и обмена событиями.
4.  Рабочая схема `RETURN_PROPERTIES` и `bizproc.event.send`.
5.  Можно ли передать результат собственного робота в штатный робот «Изменение переменной» и какие типы значений поддерживаются.
6.  Какие ограничения Маркетплейса применяются к приложению с данной функциональностью и предполагаемой коммерческой моделью.
7.  Допустимая модель подписок и самостоятельной оплаты дополнительных опций.
8.  Точные требования к тестовому порталу/NFR и доступу к REST API.

Ни один из этих пунктов не должен считаться подтверждённым только на основании предположений или примеров кода.

При продолжении проекта ChatGPT должен:

-   Считать этот документ базовым контекстом и не предлагать повторно выбирать уже утверждённые решения без веской причины.
-   Использовать название **Bitrix Randomizer**.
-   В первую очередь ориентироваться на облачный Битрикс24 и тариф "Стандартный".
-   Сначала проверять официальную документацию Битрикс24 для вопросов REST API, роботов, OAuth, тарифов и публикации.
-   Отделять подтверждённые возможности от технических гипотез.
-   Не придумывать REST-методы, параметры, scopes и ограничения тарифов.
-   Давать пошаговые инструкции, рассчитанные на последовательную совместную разработку.

-   Не рекомендовать оплачивать инфраструктуру и дополнительные подписки до проверки главных технических рисков.
-   Писать комментарии в коде.
-   Не делать самостоятельно пуши в GitHub.
-   Не вносить самостоятельно изменения в Trello.
